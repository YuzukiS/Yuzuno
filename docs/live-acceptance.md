# Independent clients and live acceptance

> Public copy: hostnames, account names and absolute machine paths below are illustrative replacements. Historical outcomes remain observations of the original private environment; these example endpoints were not contacted. Raw evidence is retained privately.

This is the continuation after the first design preview. The user approved socket access and Tauri installation and asked for Windows Tauri and WSL Core to run independently. Full access was subsequently enabled for Yuzuno development, and real socket, Windows and SSH checks now run. The earlier sandbox failures below are historical, not a current blocker.

## Implemented separation

- Core has its own executable, port, platform-local data directory and CLI options. It starts no desktop window and has no Tauri/GTK/WebKit dependency.
- The native client has its own executable and `--core-url` / `YUZUNO_CORE_URL`. It opens an embedded connection page, verifies `/api/health`, then loads the chosen Core's GUI. It starts no Core, Codex process, or WSL instance.
- The frontend uses its current Core origin for fetch, SSE and artifact links, including non-default ports. “Core host” replaces misleading “This computer” labels when the client and runtime are on different operating systems.
- Windows-to-WSL defaults to `http://127.0.0.1:4317`, following [Microsoft's localhost forwarding documentation](https://learn.microsoft.com/en-us/windows/wsl/networking). Core remains bound to loopback. No LAN listener, portproxy rule, firewall change, or OS networking-mode change is installed.
- Core connection permissions only apply to the embedded connection page. The selected Core origin can receive only the appearance command, restricted to a light/dark enum and rechecked against the active window URL. It receives no filesystem, process, or connection-selection permission. The window and Core have separate lifetimes.

Use the [root run instructions](../README.md), [native client instructions](../desktop/README.md) and [browser acceptance runner](../web/README.md). Closing the desktop should leave the Core PID and active turns intact; restarting Core is a separate recovery test.

## Real acceptance completed

### Multi-Agent slice, isolated from daily use

The new implementation runs on **port 4327** with its own data, task folders, build output and asset snapshot. The daily Core on port 4317 and its `web/dist` are not replaced. All new GUI checks use disposable headless Chromium profiles; this slice does not claim a new Windows WebView2 acceptance or manipulate the user's native window.

- [Three actual GUI-created Agents](../acceptance/multi-agent/exercise-report.json): two execute locally in WSL, one on the Mac mini. All complete real model Turns, write separate reports, and open the report at line 2 through the GUI. Reload keeps Agent/Thread identity and history.
- [Recovery evidence](../acceptance/multi-agent/results.json): a remote command finishes while the SSH tunnel is gone; reconnect restores the original Turn and one unread completion. Core restart restores the same remote runtime and all three Sessions. A completed remote Session also survives replacing its native runtime.
- The same report covers a real hard kill of the owned native app-server during execution. Recovery keeps the Thread and restores the Turn as `interrupted`. Its old tool item still lacks an exit result; the GUI labels that item **Unconfirmed**, rather than claiming the command resumed or completed. Machine reboot and lossless tool resumption are not asserted.
- [GUI approval](../acceptance/multi-agent/gui-approve-report.json) and [GUI Interrupt](../acceptance/multi-agent/gui-interrupt-report.json): an approval created offline is replayed, and one Allow once runs only the inspected fixed print command. Interrupt stops the designated Turn through the native protocol. Transport state, Pending and unread evidence remain separate.
- [Visual review](../acceptance/multi-agent/remote-visual-review.json): 1440px and 900px, both themes, 20px reading size. Machine labels and state badges wrap; connection controls align with the conversation. No page overflow or browser errors in these views. Long laboratory names require independent Rail scrolling at the narrow size; a complete screen-reader and native DPI review was not performed.
- [Real Catch-up comparison](../acceptance/multi-agent/catchup/real-run-1/comparison.html): three actual Turns, sixteen source records and five generated summaries. All fifteen source-navigation paths work, and read/Pending state stays unchanged. The three original final replies total 164 characters; the summaries total 605. This validates provenance, not faster catch-up or independent semantic accuracy. A varied sample of real work and the user's reading review are still needed. The GUI still displays source records; automatic model summaries are not a finished feature.

These checks caught defects that unit coverage alone had missed. Replayed approval action IDs now change when the connection is replaced, while their unread evidence remains deduplicated; an old page cannot authorize a new connection's request. Native history can synthesize `item-N` IDs, so message occurrences are reconciled in order while preserving live IDs for source links, rather than appending duplicate prose. On macOS, a hard-killed Codex can leave a private socket symlink; recovery removes only that owned link after confirming the old runtime and listener are gone, never its external target. Original failed observations remain in the reports.

The final [read-only history check](../acceptance/multi-agent/history-alias-recovery.json) confirms the repaired message appears once, conversation search finds that one occurrence, and both search and Catch-up reach the retained original message IDs. The interrupted tool displays Unconfirmed; no read/unread/Pending value changes and no mutation requests occur. The [daily-instance check](../acceptance/multi-agent/daily-verification.json) confirms the original daily Core process and assets remain unchanged.

The transport uses system OpenSSH and `tokio-tungstenite`, with an exiting Python helper and an independently running official app-server. The Mac mini uses an isolated official Codex 0.162.1 tree under `~/.yuzuno-next/tools/`; the global Codex and account login are unchanged. There is no general Harness adapter, remote worker, account manager or service-management framework.

## Windows development dependencies

Only the Windows desktop build needs the Microsoft compiler toolchain; WSL Core still needs no GTK/WebKit/Tauri packages. The user approved the following minimal installation after reviewing the original installer choice:

- Visual Studio **Build Tools 2022**, not the full IDE, installed at `C:\BuildTools\Yuzuno`.
- Explicit components: `Microsoft.VisualStudio.Component.VC.Tools.x86.x64` and `Microsoft.VisualStudio.Component.Windows11SDK.26100`, plus installer-required dependencies. No workload or recommended-component option was selected on the successful attempt.
- Rust lives in `%LOCALAPPDATA%\Yuzuno\toolchains`; global PATH was not modified. Windows build artifacts are under `%LOCALAPPDATA%\Yuzuno\build\desktop`.
- Existing WebView2 was reused. The Microsoft installer completed without requiring a reboot. `winget list` can see the installed Build Tools via its system registration; it is not claimed to have been installed through winget or mapped to a winget source ID.

The initial larger Build Tools attempt was cancelled at Windows UAC and did not complete. After the user selected the minimal components, the normal official installer succeeded. Future dependency installations should prefer the existing package manager where it supports the required setup.

## Runtime findings

The Mac mini target `tester@192.0.2.10:22` has now been reached over real SSH. Its existing Codex 0.156.1 with the selected model produced a native code-mode-host handshake timeout. A separate official Codex 0.162.1 npm installation in an experiment-only temporary directory can execute real tools; this run also used a different default model, so the improvement cannot be attributed to version alone. Existing remote installations, Agents and the default daemon remain untouched. All six [remote checks](../experiments/runtime/remote-live-observations.json) passed: a real command finished while SSH was disconnected, the same Turn was completed on reconnect, an approval raised offline was replayed and answered for the fixed test command, and completed history survived restarting the owned runtime. Missed item notifications were not replayed individually: `thread/resume` plus `thread/read` recovered their historical results. This does not validate a durable event cursor or managed `daemon bootstrap`. See [the runtime report](../experiments/runtime/LIVE-ACCEPTANCE.md).

Earlier Windows and WSL native Claude CLI status calls identified two different subscription accounts. WSL successfully completed a small real model task and resumed the same Session with its prior context; the earlier Windows inference attempt failed with expired OAuth. After the user completed official Windows login, a [read-only identity recheck](../experiments/runtime/claude-login-recheck.json) found that both platforms now report the same account. The continuation stopped before model execution. The earlier OAuth failure is historical, and the latest login metadata does not prove inference works or complete dual-account acceptance. No credentials were copied or substituted. Windows was only a convenient existing second-account environment, not a product requirement. Officially supported separate `CLAUDE_CONFIG_DIR` directories can host multiple claude.ai accounts entirely within WSL. Default and explicit `CLAUDE_CONFIG_DIR=~/.claude` on WSL are still the same physical store and must not be counted as two profiles.

## Remaining acceptance and next step

1. Local Codex work can now be tried in Yuzuno itself. When developing Core, keep the instance hosting the coding Agent separate from the instance used to test new code, with different ports and data directories. Restarting the hosting Core is not lossless continuation of an active tool.
2. The user has reviewed the [Catch-up reading comparison](../experiments/catchup/output/comparison.html) and said it is useful, then requested the source navigation now implemented. This is qualitative feedback; no timed questionnaire or independent summary-accuracy score has been measured. The GUI's current Catch-up view still uses original records rather than a completed model summarizer.
3. Dual-account acceptance can be completed with two genuinely separate, officially authenticated WSL configuration directories when available. There is no need to require another Windows login, and this is not a blocker for local Codex use.
4. The two-local/one-remote Slice now runs in the isolated GUI at `http://127.0.0.1:4327`. Its standalone recorded Catch-up experiment is served at `/catchup-comparison.html` for review; it is not a live summarization endpoint. The next useful step is a small genuine development task in this build and a more varied reading sample, followed by a minimal WSL Claude integration. An account manager, Worker and continuous Observer remain outside this slice.

That interrupted attempt was not called a passing lifetime test.
