# Delivering a code change

The order below is the usual shape; your project's instructions decide who may push, merge or deploy, how many review rounds are allowed and which tests are required.

## Dispatching an executor

A lead of the task's Project, or the user, dispatches a task to a new executor with `task_dispatch` and `executor`: `{}` for a general executor, `{templateId}` for one made from an executor template. `executor_templates_list` lists the templates, each with when to choose it, its delivery mode (`pr`, `direct-commit` or `none`) and its steps, which are descriptive: Core does not track them. The executor starts when its machine has a free executor slot, and `task_get`'s `executorSlot` shows its place in the queue. If its start fails, Core rebuilds it once as a new dispatch; if that fails too, Core blocks the task and mails the dispatcher.

- **Where it runs.** `executor.machineId` is a machine's id, `local` for the Core host, or `auto` for Core to choose one now: a free executor slot first, then the most spare Jobs memory, then CPU, recorded as `executorSlot.choice`. Unset, it is the template's machine, else the Core host. The machine is the dispatch's choice; a template's machine is only its default.
  - `machines_list`, for leads only, gives each machine's id and name, the harnesses its executors can use, its executor slots (`limit`, `running`, `waiting`), whether an Agent there is connected now, the user's last manual check, and `projectFolder`. It gives no address, user, port or key. The user adds machines and sets each one's executor limit.
  - On the Core host the executor works in the dispatch's worktree, else the Project's folder there. An Agent's dispatch may name only the worktree the user registered on the task, or a folder inside the Project's (`folder_not_allowed`). Core makes no folder.
  - On another machine it works in the Project's folder on that machine, which must exist (`no_folder`; check `projectFolder`). A worktree is a path on the Core host, so such a dispatch can't carry one. The executor starts in that folder itself, not in a worktree of its own.
  - OpenCode executors run on the Core host only, and a machine that keeps its Agents contained runs no Codex executor (`machine_contained`). An unknown id is refused with the machines this executor could use (`machine_not_found`).
- **Its name in the sidebar.** Give the task a `shortName` before dispatching (`task_create` or `task_update`): what it is about in plain words, one line of at most 16 characters, such as "Export settings", not a key, a number or a PR. The executor's row shows it as line one, else the task's title. A ring beside it shows one of five states at a glance (working, needs you, done, failed, idle); needs you means it waits for an answer, such as a gate's Ask. A pill says a state that holds, such as queued with its place, under review or ready to merge, and line two says what it is doing, its blocker or what it asks.

## Gates

A template step of `kind: gate` is a point where the executor waits for an approval. Its `approver` is `user` (also when unset), `lead` or `either`. Steps count from 0, as `executor_templates_list` lists them; the dispatch mail shows each gate as `gate (<approver>): <label>`.

- At a `user` or `either` gate, the executor asks with its own Home Ask that names it: `ask: {question, reply, gate: {taskId, step}}`. Core takes it only from that task's executor (`gate_not_yours`) and only for a gate step of its template (`gate_step_unknown`, which names the template's gates). Home lists it in Needs you, the sidebar shows the executor as needing you, and its Overview shows the step waiting with the Ask's card. An answer there, on Home or in its Conversation is the same Ask.
- At an `either` gate, also mail your dispatcher: its mailed approval counts too, and you then resolve your Ask. At a `lead` gate, mail your dispatcher instead of asking on Home.
- Core does not stop an executor that goes on without the answer, so don't go past the gate before it; work that doesn't depend on it may go on. For an irreversible step, say the command, target, risk and rollback in the Ask.

## Candidate

- Commit, push the branch, and create or update the PR — with `github_pr_submit` (asynchronous; the result arrives by mail) or with the project's own git tooling.
- Link the PR to the task with `github_links` so reviews and CI can refer to it. A new commit is a new candidate: CI, reviews and your result must name the exact head.

## Explicit delivery flow (when available)

- Use `delivery_get` to read the task's actual review settings (its project's, else the Workspace's) and any existing flow. Only explicitly authorized tasks use `delivery_enable`: one linked PR, full base/head, and a cap of one or two registered review attempts. The assigned open local Agent receives the results. Existing matching manual reviews are reused. Its rounds also count toward the PR's two started review rounds across tasks, full, incremental and continuation alike: authorization checks that first, without reserving anything, and the start checks again atomically.
- Submit `task_submit_result` with status `review`, your original `dispatchId` when required, and the exact `delivery` candidate returned by `delivery_get`. This atomically queues that authorized review and exact-commit CI subscription. An ordinary result without `delivery` starts neither. Finish the turn or do independent work; do not also start a replacement review.
- A new push invalidates old readiness. After checking a completed review, `delivery_continue` explicitly authorizes the next candidate within the original cap, followed by another matching result. Registered failed attempts consume the cap too, and every round also needs one of the PR's two started review rounds across tasks; if that limit is reached while starting, the round records `limitRefused` and waits for a person, without retrying. An unfinished or `unknown` review cannot be replaced this way: retain its review/request IDs and reconcile manually.
- `delivery_get` shows evidence, observation times and the next action. `ready_to_merge` refers to the fixed review and observed GitHub Actions workflows, not permission to merge, branch-protection approval or deployment. `delivery_stop` prevents future automation without cancelling already running operations. Do not emulate these tools on an older Core.

### Lifecycle cleanup (T-80 source; requires a Core with this change)

- Task done/cancelled/archive and an observed PR merge close automatic delivery and retain its terminal state, reason, time, operation IDs and evidence. `ready_to_merge`, `waiting_fix` and CI failure are not terminal. Reopening a task does not reopen its finished delivery or reset the review cap.
- `delivery_stop` remains idempotent after the task is closed. It releases only that flow's CI interests, including prior rounds; a manual subscription sharing the same ID remains independent. It does not cancel a running reviewer or any remote workflow.
- PR candidate subscriptions close on task closure or an observed PR merge. Other tasks/Agents sharing a watch retain their own interests. An explicit run subscription can still finish post-merge verification after task closure; Core retains it until its latest observed attempt finishes and its completion mail is recorded (or its seven-day expiry / explicit unsubscribe). Subscribe to the actual main run URL for this purpose, not the merged PR URL, or, where the Core has commit watches (below), to the merge commit before its run exists. A commit watch is retained after task closure until every run it found has finished at its latest attempt with its mail recorded, and complete, successful reads after your request have seen nothing new for ten minutes. A new run or attempt, a changed status, a failed read or an incomplete run list starts those ten minutes again. This is the product's bounded discovery window for later workflows of the same push, not a guarantee that no later workflow will start.
- `ci_unsubscribe` explicitly stops all interests in your chosen subscription. `ci_list` retains inactive subscriptions, interest closure reasons, runs and mail history. To watch a same-SHA rerun after cleanup, use a **new** `ci_subscribe` requestId (and reopen the task for a PR candidate; a specific run may be subscribed on a done task). Replaying an old requestId only retrieves its existing subscription and never renews or reactivates it. A new request needs a fresh run observation; it cannot treat a cached old green as new verification.

## CI

- `ci_subscribe` with the PR or run URL and the exact head SHA sends one mail per completed run attempt. A newer head needs its own subscription.
- An open SSH Agent subscribes for itself like a local Agent, under the same task, ownership and limit rules; Core reads GitHub and the results arrive in its mailbox, with nothing run on its machine (T-49 source; requires a Core with this change). A Core without it refuses an SSH Agent with "Choose an open local Agent": there a local Agent has to watch the run and pass the result on. Automatic delivery (`delivery_enable`) still needs a local task owner.
- After a merge, watch the merge commit itself, with no need to wait for its run to appear.
  - Pass its commit URL (`https://github.com/{owner}/{repo}/commit/{sha}`), `expectedSha` set to that SHA, and the exact `branch` and `event` of the runs to watch. For a merge to main that is usually `main` and `push`; check the repository's workflows rather than guessing.
  - Until a run exists the watch shows `waiting_for_run` and reads less often: every 30 s for ten minutes, every two minutes until an hour, then every ten minutes. The Agent rail shows it as waiting for its first run, still monitored, with its last successful check; only a failed or overdue read turns that into Check CI.
  - Only runs of that SHA, branch, event and repository count. A PR run of the same commit, another branch's run or a fork's run never does, and a newer main commit never replaces the watched one.
  - Each finished attempt mails once. If no matching run was observed by the seven-day expiry, one mail per subscription says so, with any failed reads or an incomplete run list. It reports what Yuzuno observed, not that GitHub never had such a run, and it is not a pass. Replaying an old requestId neither renews the watch nor mails again.
- `ci_get` returns the run as Core last observed it and one page of its jobs and steps, which Core reads through a short shared cache (an expired cache means one conditional GitHub read); each part carries its own observation time. `ci_refresh` asks GitHub about the run and its visible pages now, within GitHub's poll interval and cooldowns. Neither reruns or cancels CI.
- A known `runKey` can be checked once with `ci_refresh` even when its monitor is stopped, expired or paused. This does not resume or renew monitoring. `runWatched` describes current monitoring separately from the last observed GitHub status; an unwatched Running record is historical, not proof it is still running. Refresh reads the exact recorded attempt and retains old facts on failure.

## Independent review

- In releases with review policy 2, a complete, valid review that explicitly says the patch is correct and contains only P3 suggestions can conclude `approved_with_notes`. Keep those suggestions visible. P0–P2 findings, an incorrect or unknown verdict, incomplete coverage and invalid or unconfirmed output never pass under this exception. `no_findings` still means a passing review without findings.
- Read the stored `policyVersion` and `reasonCodes` with the evidence. Reasons distinguish incomplete coverage, unsupported source, model uncertainty or conflicting verdicts, an invalid report, and failed, cancelled or unconfirmed execution. Codes explain the outcome; they are not permission to ignore it. Older records keep their original verdict and raw report; do not reclassify an old `unknown` merely because its findings are P3. Passing still needs the exact candidate, CI and the project's merge authority.

- Source versions with `coveragePolicyVersion: 2` also accept a complete `source_read` of an **added regular text file** as `full_added_source` evidence. Every delivered range must name the same frozen revision, blob and mode, include its change-manifest metadata, and together cover the whole file. An empty file requires an actual successful empty read. Missing, truncated, failed or budget-rejected responses count for nothing. Modified and removed files still need their complete diff; a rename remains deletion plus addition, so reading only its new path is insufficient. Binary files, links and submodules are not eligible.
- `coverage.coveredFileCount` counts unique covered files. `deliveredCompleteDiffs` remains the actual complete-diff count; it is never increased by a source read. `coveredFiles` names the selected proof's `deliveredVia` (`source_diff` or `source_read`), `evidenceKind`, fixed identity and, for full added source, receipt numbers. A complete diff takes precedence if both forms were delivered. This coverage version is stamped when a new review is registered; absent/older versions remain diff-only, and old reports or verdicts are not reinterpreted.
- From `coveragePolicyVersion: 3` (review policy 3), a review also records `scope`. It names its frozen base, head and merge base, and the policy it used. For every changed path it gives each side's blob and mode, every fact Core found for the path, and a `state` that names the first fact in this order:
  - `covered`, with T-134's `evidenceKind`;
  - `excluded`, by a rule of the base's policy;
  - `unsupported`, as `binary`, `not_utf8`, `symlink`, `submodule` or `special_file`, with its side and, for a regular file, its content's SHA-256;
  - `budget_exhausted`, either `diff_exceeds_context` (the complete diff is larger than the whole review context; a large file with a small diff stays readable) or `context_exhausted` (a budget ran out first);
  - `read_failed`, with the unresolved requests;
  - `not_read`, with any `remainingByteRanges`.

  Each fact says when it was found:
  - `before_review`: links, submodules and policy exclusions, known from tree metadata alone. The reviewer is told not to request them, and no changed blob is fetched for them.
  - `during_review`: something the reviewer's own request ran into.
  - `after_review`: Core's bounded check of what was left uncovered, made only once the reviewer has finished and outside its deadline, so it can't take budget or time from the review. A cancellation or its own time limit only stops the check (`scope.checkAfterReview: "stopped"`), never the completed result. Its gaps are recorded as `not_checked_after_review`.

  Such paths set `unsupported_source`, `diff_too_large` or `scope_excluded` and keep the review incomplete. None of them is ever "covered", and nothing here approves a review.
- **Scope policy.** It is the file `.yuzuno/review-scope.json`, read only at the PR's frozen base, so a head can't exempt itself. Its schema is `{"version":1,"exclude":[{"path":"exact/path" or "dir/**","reason":"…"}]}`, with at most 50 rules and 8 KB. Rules use no other globs and no `.`, `..` or absolute paths, and the policy file itself is always reviewed.
  - Without the file, every changed path is in scope. A file that can't be used excludes nothing. It adds `scope_policy_invalid` only to an incomplete review, so a review that covered every path still passes.
  - When excluded paths are the only gap, `scopeConclusion` shows the verdict within the policy's scope. It is for information only: the review's conclusion stays `unknown`, and delivery ignores it.
- **Repeat rounds.** If the latest completed round of the exact same base and head recorded such permanent gaps, `review_start` refuses before a round exists and names them. Report the gap instead, with any evidence. `acknowledgeUnreviewable: true` reviews the other paths anyway. It only acknowledges the gap: it is not an approval, doesn't lift a round limit and doesn't change the result.
- **Evidence for an uncovered path.** `review_evidence_add` records a source review, build provenance, an artifact hash, a signature or a behaviour test. It can reference another review or Job of the task, a CI run of the same repository, or an https link.
  - The record is bound to one review's base, head, merge base and that path's blobs and modes. It shows as bound to this candidate only when all of these match.
  - After a new head it shows as another candidate's. Add it again with `previousEvidenceId` to bind it to the new review; the old record stays.
  - Core fetches and verifies nothing, and the note is yours. "Bound to this candidate" is an identity match only. `artifactMatchesHeadContent` says only that the registered SHA-256 equals the hash of the fixed Git content Core read, not that the referenced Job's or link's artifact was retrieved or checked. Evidence never changes a review's conclusion or whether it passes.
  - The permanent gaps are paths no further round of the same head can cover. That says nothing about whether any other gap may be retried or continued.
- **Continuing a round** (Cores newer than 2026.10.19-core.12). `review_continue` asks for a bounded continuation of one completed round of the same frozen snapshot, for the changed paths it left `not_read` or `read_failed`. Its `baseSha` and `headSha` may be left out: they are the parent round's.
  - It is a new isolated reviewer run with its own record, round number and cost, not a resumed session. It gets only what the parent round left of its 160 calls, 1.5 MB and 900 000 ms, to the exact millisecond; nothing is refilled.
  - A PR gets at most two started review rounds, full, incremental and continuation alike, counted across every task linked to that PR. A round counts unless its record, made with a ledger, shows it reached no verdict:
    - it failed before its native start was recorded, so it started nothing;
    - or its harness itself reported a failure before any report: its only reason is `execution_failed`, with no conclusion, findings or correctness verdict (Claude ends it `failed`, Codex `unknown`). One that read nothing but the change manifest never counts. Of those that read source first, only the PR's first doesn't count; every later one does.
  - Such a round records the decision as `roundLimit` (`counts`, `read`, `why`), shown in `review_list` and `review_get` and in its end-of-review line on the task. Every other round counts: a report of any kind, a cancellation, a deadline, a restart, an unconfirmed shutdown, and older rounds without a ledger.
  - Core refuses it before it exists, starting no model, when the parent:
    - isn't `completed` with `ledger.nativeCompletion: "confirmed"` (its native run completed and shut down, and its report was stored before the check after the review);
    - predates usage ledgers (every round recorded before such a Core);
    - is itself a continuation or already has one;
    - stopped at a terminal limit or has nothing left to read;
    - was judged with another snapshot, policy or reviewer setting;
    - left too little of its budget.
  - Paths no review of the snapshot can cover need `acknowledgeUnreviewable: true`; the result then can't pass.
  - Before its reviewer starts, Core re-fetches the snapshot and checks that it is the parent's, that every response the parent delivered still matches its recorded `responseSha256`, and that the unread paths fit the remaining bytes. Otherwise it ends `failed` with `continuation_refused` and `nativeStartedAt` unset: no model ran, and the parent's one continuation remains.
  - Under an authorized delivery of this candidate it must be one of the delivery's attempts, so use `delivery_continue` first. Manually it is a counted round like any other, and your project's round limit applies.
  - Its reviewer gets the parent's conclusion, findings and coverage as an earlier model's untrusted output, never as instructions. Re-sent material counts against the remaining bytes.
  - Its coverage, scope and conclusion are over both rounds. Each covered path names the review whose reads proved it (`byReview`). The parent's unresolved requests stay unresolved until it covers their path. The parent's findings are carried unchanged with their `origin`, and a blocking finding from either round blocks; one not repeated isn't resolved. The parent's own record never changes.
  - `ledger` records each run's calls, bytes, operation time and the harness's own usage report, and for a continuation the `cumulative` total. Claude's reported cost is its own estimate, not a bill; Codex reports none, so it is `unknown`, never 0.
  - A round whose native run completed and shut down but which Core restarted during the check after the review finishes as `completed` with `scope.checkAfterReview: "interrupted"`; without that confirmation it is unknown, as before.
  - After a lost reply, repeat the same requestId. A continuation left unknown by a restart is never run again; reconcile it from its record.
- **Reviewing a new head incrementally.** `review_start` with `previousReviewId` reviews a new head of the PR after one completed full round of another head.
  - It is a new round with its own record, a normal budget and its own cost. It counts toward the same two started rounds per PR, full, incremental and continuation alike.
  - Only that round's proofs of changed paths whose status and both sides' blob and mode are identical, under the same merge base, carry over, each naming that round (`byReview`) and the head it read (`provedAtRevision`). Every other changed path is a target the reviewer must read completely. A new merge base makes every path a target.
  - A carried proof only shows that an earlier reviewer read that diff. The reviewer is asked to check how this head's changes affect carried paths and to say what it checked; if it can't tell, the verdict is unknown.
  - Core refuses it before it exists, starting no model, when the earlier round isn't a completed full round with a confirmed native completion and a ledger, used another reviewer or policy, or reviewed this same head (that is `review_continue`'s case).
  - Before its reviewer starts, Core checks that the earlier round's retained responses still match their hashes, and that the fetched head isn't the earlier one and changes something. Otherwise it ends `failed` with `incremental_refused` and `nativeStartedAt` unset, and it doesn't count.
  - The earlier findings stay, with their `origin`, and a P0–P2 one keeps blocking. One is settled only when this round marks it `fixed` with fix paths whose head object (blob and mode) differs from that head's and that this round read completely itself. A path that left the PR, a finding not repeated, or a missing, duplicate or invalid answer settles nothing; the finding stays `still_valid` with the reason. Settled ones are listed in `settledFindings` with what settled them. The earlier round's own verdict isn't carried.
  - After a new merge base, Core also reads what changed between the two merge bases from its own store, blob ids and modes only (`incremental.baseChanges`). A finding may then be settled `fixed_by_base` instead: the round names base paths from that list, added or changed there, that it read whole at their new object with `source_read`, and the finding's own path is a target it read completely that didn't change in the base. Code that moved into the base (the finding's own path changed there, or left the PR) stays a finding. Only such rounds are offered it; every other round's instructions and schema are unchanged. If Core can't read the change, or lists only part of it (more than 2,000 paths), nothing is settled by the base.
  - `ledger.cumulative` shows both rounds' calls, bytes and time, and each run's own usage report under `runs`; a cost one of them didn't report stays unknown. The earlier round's record never changes.

- Check `review_list` for the same base and head first, so a round is not started twice. MCP lists compact summaries, 20 newest first: fixed identity and revisions, status/conclusion and failure reasons, finding count, coverage counts and scope-state counts. Follow `nextBefore` as `before` while `hasMore`, keeping the same task; newly inserted reviews appear on a fresh first page. `outdated: null` means the current version is unverified. Missing historical coverage or counts stay `null`, never zero or passing.
- List rows omit findings bodies, reports, context reads, ledgers and per-file evidence. Use `review_get(taskId, reviewId)` (default `view: "summary"`) for findings and uncovered paths, or `view: "full"` for the original stored report and evidence. GUI REST lists keep their existing full records. The list/get tools read retained local records without refreshing GitHub. `review_list` declares a structured output schema including `{error: string}` tool failures (`isError: true`); a retained failed review is a successful read (`isError: false`) with its own status/error. `review_get` has no output schema yet because its historical full evidence varies by policy version.
- Start it yourself with `review_start` on the task's PR link and the fixed base and head, once the candidate is frozen and your targeted checks pass. It may run while CI runs. Finish the turn; the report arrives by mail and `review_get` reads its summary (`view: "full"` adds the original report and per-file evidence). If you were dispatched, your dispatcher gets a copy when the round ends: quiet once it completed, ringing when it failed, was cancelled or is unknown. A full round counts like any other: once the PR used its two started rounds, `review_start` refuses before the review exists unless the user or the task's current active dispatcher passes `beyondRoundLimit: true`. That is recorded on the round and judged the same way; it is not available to an executor, an inactive dispatcher or an incremental round.
  - Take `baseSha` and `headSha` from the PR link (`github_links`, `snapshot.baseSha` and `snapshot.headSha`). The PR's base is the commit GitHub recorded for it, often behind the target branch's current tip: do not substitute main's head. If you are unsure of the base, omit `baseSha` alone: the round reviews your fixed `headSha` against the PR's current base.
  - An abbreviation of 4 to 39 hexadecimal characters works too, if it is exactly one commit of the link's repository: Core resolves it on GitHub and records the full SHA. An ambiguous one, a branch or another revision expression is refused, not guessed. Task materials take abbreviations the same way, resolved in their `repositoryId`. There a full SHA is asked of GitHub too: one GitHub says is not a commit of that repository is refused, and one it cannot answer for is saved with `shaCheck` unverified and why, which each dispatch asks again.
- Verify each finding against the code. Fix what is in scope, then give the new head its own CI and the next round as the project allows. Raise scope or verdict disputes with whoever owns that decision.
- A review is evidence, not approval: it does not merge, run code or complete the task. Failures of the review service itself are not review rounds; report them rather than retrying without limit.

### Fixed-source tool errors

Where the running reviewer advertises it, `source_search` accepts an omitted first-page `cursor` as `0:1`; subsequent pages require the returned `nextCursor`. This is a reviewer tool contract, not an additional Workspace tool or permission. Older Core versions may still require the initial cursor explicitly.

The reviewer must correct failed arguments using the returned error and schema. Three identical unsuccessful calls stop the review early with incomplete coverage; the overall 160-call / 1.5 MB budget remains unchanged. Failed requests remain in the report. A successful correction can resolve a parameter failure only within its recorded source scope, and does not itself prove any additional diff or line coverage. Missing source, mismatched revisions/paths, partial range recovery and exhausted budgets remain incomplete. Inspect the original receipts, `resolvedByReceipt` and `terminalLimit` before interpreting a recovered or failed review; do not erase a failed attempt or launch an extra round without authorization.

In source versions supporting `searchRecovery` evidence, a non-parameter `source_search` failure can recover through successful pages at the same frozen revision and literal query, beginning at the same parsed cursor. Core compares the prefixes' actual matching path sets in that frozen tree; adding or removing a trailing slash alone proves nothing (`src` may also match `src-extra`). Follow every returned `nextCursor` until the chain ends. Partial chains, skipped source entries, other failures and terminal limits remain incomplete. The report retains the original failure, path-set fingerprint, successful receipt chain and final `resolvedByReceipt`. This source capability does not imply it is deployed on an older connected Core or repair the underlying I/O failure.

In source versions supporting `recoveryReceipts` evidence, a failed `source_read` range recovers once successful reads of the same frozen revision, path and blob have delivered every requested line, including reads made before the failure. `recoveryReceipts` lists those reads and `resolvedByReceipt` names the one that completed the range. A range over 500 lines is recorded as `invalid_arguments`. Reads of another revision, path or blob, requests that delivered nothing, other failures and terminal limits still leave the review incomplete. Older connected Cores count only reads made after the failure, and a completed review keeps the conclusion it recorded.

## Merge queue

Where the user has turned the queue on for a repository, Core merges a reviewed PR itself. That switch and the repository's queue settings below (policy, reverts, release grouping) are the user's, in the Project's repository settings; no Agent tool changes them. While the switch is off, Core writes nothing to GitHub. Every check reads GitHub afresh, and Core never reruns CI. [The merge queue design](../../../../docs/merge-queue.md) has every check, state and reason.

- **Releasing.** `merge_enqueue` puts one PR head in the queue. The user may release it, or the task's active dispatcher when it is a lead of the task's Project; the task's executor never may, and a task with no active dispatch is the user's to release. The PR must be open and not a draft (a draft stops the entry with `pr_not_open`), linked to the task, its repository linked to the task's Project, and its base must be the repository's default branch.
  - Releasing states that the project's review pair is complete. Core refuses the head unless the last completed review round of the PR reviewed it and passes (`no_findings`, or `approved_with_notes` with P3 notes only), and no round at that head found a P0–P2 issue.
  - A round reads text only, so an image, icon or font the PR adds or changes leaves it `unknown` (`unsupported: binary`). When those files are its only gap, the reviewer said the patch is correct and found no P0–P2 issue, the releaser may check them and list each in `acknowledgeBinaries` with the SHA-256 of its content at the head. Core reads each file at the head and refuses with `binaries_refused`, naming the file, unless the list is exactly those files and each is a regular file of at most 2 MiB with that SHA-256 whose leading bytes are an image or font format (PNG, JPEG, GIF, WebP, ICO, ICNS, WOFF, WOFF2, TTF, OTF). Any other gap still refuses. The entry and the task record the acknowledgement; the round stays `unknown`, and a new head needs a new release.
  - A P2 the user accepted as intended (a behaviour they chose) may be acknowledged in `acknowledgeFindings`: every P0–P2 finding of the last completed round, each by `reviewId`, `index` and `title`, the round otherwise complete with a verdict. A P0 or P1 never is. The user releasing needs nothing more; a lead cites in `userReply.key` a live Home ask of the task's Project that the user replied to, unchanged since, whose title, question or body names the PR (`#number`) and the finding (its title, or its id: the review id's first 8 characters, a slash and its index, such as `b3e3a2a5/0`). Ask before releasing, and resolve the ask after it. Core reads the reply and records it on the entry and the task, or refuses with `findings_refused`, naming what didn't match. The round's conclusion stays, and a later round or a new head needs a new release.
  - The workflow named `CI` must run on the head; `requireWorkflows` names others that must too.
- **A head that adds only merges.** A head committed after the last round still passes when all it adds are merges that need no review of their own. There may be at most four, each a merge of two parents whose first parent is the commit before it. Each must bring in a commit already on the base branch, or the head of a passing round of a PR of this repository, with no P0–P2 finding at that head and its base on the base branch. Core redoes each merge in a private object store and admits the head only if every one is clean and gives exactly the merge commit's tree.
  - So after a passing round you may merge main, or a reviewed PR your branch stacks on, into your branch, and the queue still admits the head. A merge that resolved a conflict, or any other commit, needs a new round: the release is refused with `review_not_passing`, naming the commit.
- **The gate**, by the repository's policy:
  - `strict` (the default): CI tested exactly the merge of the current main and the head. If the PR's own CI tested an older main, Core opens a CI-only batch PR on the current main and waits for its CI. That batch may be stacked on the batch ahead of it, in a chain of up to four that merge in order. A red main CI run since the release (or its last retry or unpause) stops the entry with `main_red` and pauses the queue.
  - `relaxed`: the PR's own CI is green at the head, on whatever main it tested. Core's own merge of the head into the current main is clean (a probe branch, with no PR and no CI). And main CI is not red now; while it is, the entry waits.
  - Under both, every workflow run on the head must finish green, and a PR that GitHub reports as conflicting stops at once with `conflict`.
- **Merging.** Core sends one merge request, for a merge commit pinned to the head (never a squash or a rebase). An uncertain answer is never retried: the entry stops with `merge_unknown`. Core then checks that the merge commit's parents are main and the head and that its tree is the tested one, removes its batch or probe, and follows main's push CI on the merge commit. Green ends the entry `done`; red ends it `done` with `main_red`.
- **Pauses.** Red main CI (under `relaxed`, only after a merge), a failed or unverifiable post-check, or `merge_unknown` pauses the repository's queue. Entries are still checked but none merges, and the pause is mailed, urgent, to the entry's releaser and the leads of the Projects the repository is linked to.
  - `merge_unpause` (a lead of a Project the repository is linked to, or the user) ends it and re-anchors the waiting entries at the current main. Unpausing while main is still the red commit accepts that one red run; each entry still needs its own green CI. A red-main pause also ends by itself once CI on a newer main is green.
  - Where the user allows reverts for the repository, `merge_revert` (a lead or the user) reverts a merge whose entry ended with `main_red`, as a revert entry that needs no review round.
- **Release grouping.** Where the user allows it for the repository, Core tags each PR it merged once the post-check held. A PR with no milestone gets the repository's newest open one, and every PR gets its task's label `task:<key>`, which Core creates first when the repository has none. Tagging never changes the merge, the entry's state or the queue. A tag Core could not set is named on the task, to set by hand.
- **Which head.** `merge_enqueue` stays pinned to the exact head you checked: give its full SHA (either case). A head that is not the PR's is refused before anything is written, naming the PR's head and the head the last round reviewed in full, to copy. `ci_subscribe` takes a PR's or run's head by its first 7 or more hexadecimal characters and watches the full SHA Core reads; for a commit URL it needs no `expectedSha`.
- **Following an entry.** `merge_get` reads one entry, or a task's newest, with its state, reason, merge, newest history and evidence; `view: "full"` adds the last check as read and the whole history. The merge writes answer with the same summary. `merge_list` lists short rows, newest first, 20 a page unless you give `limit` (up to 50); pass `nextBefore` as `before` while `hasMore`. Core writes the outcome and its evidence to the task, and mails the releaser and the task's executor.
  - `merge_retry` checks a stopped entry again from the start; `merge_cancel` cancels a queued, waiting or ready one. Either is for the Agent that released it, or the user.
  - After a `conflict` stop, the executor merges the current main into the PR branch, resolves the conflict and pushes. That head needs a review round of its own and a new release.

## Result

- `task_submit_result` on the same task: exact head, CI run, review identifier and conclusion, tests and their scope, known limits, and links. Pass `dispatchId` when you were dispatched and your tools accept it.
- Use status `review` unless you were asked to report `done`. A result along the way (a plan awaiting approval, one slice of several) uses `doing` where your schema offers it, so the task stays in progress; a `delivery` candidate always uses `review`. Do not describe a merge or deployment you did not observe; after someone else merges or deploys, their record states it.
- Where `task_submit_result` offers `outcome`, report up to 20 criteria with result-local `id`, `label`, `report`, `reportedStatus` (`met`, `not_met`, `unknown`) and `artifacts`. Each artifact names the same task's `jobId`, its exact `attempt` UUID from `job_get` (not a stage's attempt number), its relative `path` and recorded lowercase `sha256`. At most 10 references per criterion, 40 total and 32768 UTF-8 bytes are accepted. Core requires the retained Job attempt's checked artifact to match; a missing hash, failed check, wrong attempt or another task's Job rejects the entire submission. A match establishes recorded file identity and structure, not whether a criterion is satisfied. Use an empty artifact list and an honest report when evidence is missing.
- Optional `remaining`, `nextAgentId` and `nextStep` are the author's handoff report. Core snapshots the suggested Agent's identity without assigning the task or sending that Agent mail. The existing dispatch's result notification is unchanged. Each result keeps its own `id`, `taskVersion`, author, time and acceptance context: the dispatch's frozen acceptance when dispatched, otherwise the saved registration; missing context stays unspecified. Later edits and submissions do not rewrite that report.
- `task_result_get(taskId)` reads the latest submitted result and its newest result-history page. Supply `resultId` to read a specific retained submission, independently of the history page. Follow `nextBefore` as `before` while `hasMore` (limit 1–20, default 10). Legacy submissions without an ID remain readable by default and in history. Artifact resolution reads retained Job records only, without reading current files or contacting machines; `recorded_match` is historical, and current availability stays unknown. `downloadable` only means the existing local artifact route can try a download after rechecking the file; remote artifacts stay on their machine. No independent verification or user acceptance record is created by a criterion report, a Job check, `done`, or `task_result_ack`.
