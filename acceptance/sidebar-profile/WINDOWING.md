# T-77：会话正文窗口验收

候选把已保存会话的正文传输、消息块与工具行的实际 DOM 挂载分开限制。Core 完整记录仍保留；用户通过历史分页、来源、轮次导航、保存消息搜索与完整复制访问其他内容。CSS 宽度变量作用域限制仍是辅助措施。

## 同条件对照

两个生产构建在一个隔离 Job 中串行测量，共用 `paired-profile.mjs`、同一脱敏 157 轮 / 6,197 items 内容、同一个两轮短会话、1440×1000、20px/light/garden、reduced motion、Chromium 153.0.8010.52。2 CPU、3072 MiB、0 swap、Node heap 2048 MiB、affinity 8,9、LP_NUM_THREADS=2；无 CPU 降速。每个版本四次侧栏操作和一组长短往返，没有重跑挑样。

时长从页面捕获实际 click 开始，经过目标 DOM 提交，再到两次 RAF；不是 Playwright 驱动调用总耗时，也不是物理屏幕显示时延。切换验证不同的合成短轮次 ID，避免旧长正文误满足就绪条件。短会话在两个版本都返回相同的完整两轮兼容响应。长会话候选响应来自隔离 SQLite 上的真实生产路由导出，浏览器服务器只重放数据，测量中不包含实际 Core 读取时间。

所有侧栏操作零详情请求，操作后仍位于底部。样式重算由 139–161 ms、约 23,400 个元素，降到 1.9–3.3 ms、132–206 个元素；Layout 由约 26–32 ms 降到 1.4–1.8 ms。候选不保留其他会话 DOM；切回仍重新读取，但只读取当前正文窗口。

切回长会话时 fetch 到原生 `Response.json()` 完成由 170.5 ms 降到 21.3 ms；response body 传输由 66.0 ms 降到 4.8 ms；responseEnd 到 JSON promise 完成由 71.7 ms 降到 5.0 ms。最后一项包含解析与调度，不能叫纯 JSON CPU。完整细目与报告 SHA 在 [evidence-v8.json](evidence-v8.json)。独立 API 行为夹具保留不同的 Agent 元数据，因此其响应为 315,779 B、DOM 1,072；不要与匹配性能夹具混为一个数值。

这些是少量 Linux 无头样本，不是 Windows WebView2、p95 或无资源限制的收益保证。两边都有 trace、CPU 采样、Observer 包装的开销；主机负载不完全相同。整个 Job 包含构建和测试，内存达到 3 GiB；基线浏览器阶段 `memory.events.max` 从 39058 增至 41208，候选阶段没有继续增长，两阶段 OOM/oom_kill 均为 0。这组时长是相同资源上限下的对照，不能把全部差额只归因于单一 DOM 操作。

## 行为与规模验证

- 生产构建与类型检查通过；UI 83、live-detail 12、plan-source 1、subagents 4，共 100 个前端测试通过。Core 窗口单元 5、API 集成 2、显式导出夹具 1 通过。
- 四个独立浏览器场景通过：旧 Core 完整响应兼容、真实 Core 窗口 API、流式阅读/原生旧页、计划/子代理集合。零页面错误、意外外连或写请求。
- 6,198 items 的单个巨轮（含约 900 KB 文本）初始响应 229,073 B，页面 386 元素。完整原文以一个纯文本 `pre` 按需打开，关闭后释放；不把巨大文本渲染成大量 Markdown 节点。
- 来源先加载目标再挂载嵌套工具并聚焦；用户草稿保留。工具关闭后卸载行，再次打开保留用户选择。完整复制包含当前页未加载的文字，保存搜索可以定位初始窗口之外的消息。
- 前后分页保留重叠内容的视口位置，测得位移 0.125 px。中段阅读时新增 150 条消息，保持原正文窗口，位移 -0.172 px；原生可见选择跨滚动保持，回到最新加载新尾页并回到底部（540 DOM / 31 blocks）。
- 手动原生旧页 → 来源与复制 → 保存正文页 → 最新 → 切走再切回，内容顺序、去重与旧页清空通过。未向 saved-only 原文入口发送仅在 native 旧页存在的 ID。
- 合成 2,000 步计划、2,000 个子代理、4,000 个 activity 的兼容满响应仍按可见行挂载。计划关闭卸载所有步骤，任意重复 activity 的来源可聚焦，最终场景 1,008 DOM。

## 数据与访问边界

`X-Yuzuno-Conversation: window` 是新的 opt-in；旧客户端默认详情响应不变。正文窗口最多 96 items / 256 KiB，单 item 超过 32 KiB 转为显式原文入口；稳定的 turn/item IDs 支持前后页与直接定位。完整的轻量轮次索引支持导航，问题和发送确认身份独立于正文窗口。Core 本轮仍读取已有全记录后投影，不改存储格式；debug 夹具中内部读取为长会话 175 ms、巨轮 191 ms，投影分别 37/47 ms。这是诊断值，不能与重放浏览器的 66 ms 相加当成线上预测，也不是 release 性能。

前端只保留选中会话的正文窗口；高度、展开选择、首次显示标记分别有 2,000 / 500 / 2,000 条上限，切换会话丢弃。外层轮次、消息块、工具行、计划步骤、子代理行共享滚动容器，缓冲随视口大小变化，折叠内容实际卸载。当前焦点和已存在的可见文本选择会暂时保留所需行。

已知限制：

- **96 items / 256 KiB 是正文预算，不是整个响应预算。** 轮次索引、问题、Pending、计划等元数据仍可随历史增长。元数据与 Core 全量内部读取是后续可优化的边界；不能声称整个系统严格常数内存。
- 显式 **Load earlier turns** 的旧 native `/history` 协议仍每页取 3 个完整轮次，只在选中会话累计，切换清空。其传输与客户端内存是本轮明确保留的兼容例外；本轮没有增加 native 页内 cursor/原文协议，也没有静默截断原文。已加载 native 消息可本地搜索和复制；未加载 native 页不在保存消息搜索范围。
- 上述 native 旧页的轮次、块与集合仍窗口化，但单个巨大原生 Markdown 消息仍可能生成较大 DOM。显式打开完整原文、既有单轮发布结果与独立 Pending/问题界面也不属于正文 item 预算。发布结果已有每轮 3 链、单条 64 KiB/32 组件的限制。
- 浏览器原生全文查找、跨未挂载区域拖选只覆盖当前 DOM；界面提供保存消息搜索、原文和完整轮次复制入口。大原文显示为可选择纯文本。无 ResizeObserver 的环境保留兼容树，不具有这里测得的 DOM 上限。

## 证据与复现

本目录脚本和摘要可提交；脱敏原始会话、API 导出、trace/CPU 文件保留在隔离 worktree 的 `target/t77/`，不提交 Git。最终 Job 输出 `target/t77/window-v8/`；terminal receipt 为 `target/t77/window-v8-terminal.json`。原有阶段一归因在 [README.md](README.md)。

`window-v8.sh` 在固定干净提交下，通过有界 Job/heavy-slot 依次构建、测试、导出、行为检查和两版本性能采样。原始 fixture SHA 固定为 `b17c868ec398ad5b23247d813aaef5e3dcf9b210bcfd2cd38e1f9f330e81c76d`。基线资产逐文件哈希验证；新导出在同一 Job 内计算 SHA，两个性能场景验证同一导出。脚本拒绝覆盖既有构建产物；不应用于日用 Core。

旧失败全部保留：v1–v3 夹具/初始导航问题，v4 返回最新的平滑滚动冲突，v5 分页锚点偏移 72 px，v6 中段布局锚点偏移 94 px。v7 修复后通过；v8 增加集合与元数据收尾后再验证通过。没有把失败数据删掉或作为有效收益样本。Job 总 CPU 107.8 s、约 133.5 s 墙钟、峰值 tasks 147、pids 上限事件 0。

独立评审 R1 发现待审批文件修改的来源按钮仍直接查 DOM，目标被数据窗口或工具行窗口移除时不能导航。修复后，该按钮与问题面板的“Original question”共用已有的按 turn/item ID 加载、挂载和聚焦流程；查看修改还展开目标 diff。缺少 turn 引用且本地无法定位的旧请求会明确提示。`window-source-check.mjs` 使用纯合成数据覆盖未加载的审批轮次、未加载的原问题、已加载的 500 工具组中未挂载的审批项，并核对草稿、待审批状态和零写入。`window-v9.sh` 对修复候选运行构建、相关 UI 测试及 source/API/reading 三组浏览器检查；v8 的匹配性能测量仍固定在原受测提交，不能当作新候选重新采样的结果。

R2 发现整轮原文端点缺少详情读取时补充的邮箱来源标记，导致复制把协作消息误标为用户输入。原文端点现在只对目标轮次补充同一可信投递来源，覆盖整轮由邮箱启动及中途插入的消息，也覆盖未加载页中的输入；不依赖正文识别，不修改保存内容。`window-v10.sh` 验证原文/邮箱/payload 合约，并把临时 SQLite 生产接口响应交给浏览器验证完整复制的作者标签；前端源码未变，明确复用 v9 生产资产。两轮独立评审均已保留，R2 后的修复不能称为已经独立复审通过。

v10 在 `ed14ab3820f72cca662e52916824ba37de14a6d7` 通过：邮箱单测 5、payload 单测 5、窗口 API 3、协作 UI 15，以及原有来源导航和 start/steer 两种真实原文响应的浏览器复制检查；页面错误和写请求均为零。Job `5dd41e03-646a-43bd-b812-6cdc225ab8c6` 的完整输出保留在 `target/t77/window-v10/`，使用相同 2 CPU / 3 GiB / 零 swap 上限，CPU 94.1 s、墙钟 96.0 s、峰值内存 3 GiB、峰值 tasks 133、pids 上限事件 0。
