# 最小 Catch-up 实验：这一轮得到了什么

已从旧 Yuzuno 的真实工程记录中选出 **4 个多 Agent 回放窗口、22 条原始记录**，制作可并排阅读的原文摘录与 Catch-up 参考稿。来源、时间边界和引用校验已运行；**没有完成独立模型生成评测或用户 30 秒阅读实测**。

直接打开 [原文与参考稿对照](output/comparison.html)，或阅读 [Markdown 对照](output/comparison.md)。[结构检查结果](output/metrics.json) 不代表语义准确率。

用户已阅读对照并反馈“有帮助”，同时明确要求整理内容能直接回到原文。这是实际的定性反馈；没有记录阅读耗时或执行下方的计时问答，不能据此宣称已经达到 30 秒理解目标。

## 原文跳转

点击 B 栏的整理正文即可定位并高亮 `nextSourceId` 对应的 A 栏原始摘录。多来源条目保留每个来源的 Agent 和时间，能够逐条打开；“返回整理内容”回到刚才点击的那条整理，浏览器后退也可返回。键盘 Enter 可以打开链接，跳转后焦点移到目标记录。

这是同页的旧 Yuzuno 摘录定位，不是新 Core 的会话深链，也不包含未导出的完整原始对话。正文保持按文本转义显示；该页面不会执行原记录里的操作或改写 Workspace 状态。使用浏览器原生片段链接，无额外依赖，禁用 JavaScript 时也仍可跳转；脚本只补充焦点和当前阅读路径。

生成器现在内联 `comparison.css` 与 `comparison.js`，输出仍是一个可独立打开的 HTML 文件。已在真实 Chromium 校验 12 个整理正文入口、25 个引用及全部 59 个页面链接均指向存在的目标，且主要来源和完整引用列表与 `reference.json` 一致；键盘、返回、多来源和 390px 窄屏检查通过。见 [导航验收记录](output/navigation-check.json)、[桌面截图](output/source-navigation-desktop.png)、[窄屏截图](output/source-navigation-mobile.png)。22 条旧库记录的来源核对及原有 5 个负例也再次通过。

## 数据与方法

- 数据源：经用户授权的私有旧版数据库 的 `trail_touches`，通过 SQLite `mode=ro&immutable=1` 读取。没有写入旧数据库，没有读取认证信息，也没有复制完整数据库。此模式没有合入 WAL，因而不声称拿到了最新完整现场。
- 窗口是事后选择的真实时间段，不是假装记录了用户何时离开或回来。没有历史已读位置、当时完整 Pending 集合或原生进程状态。
- 只保留工程内容的短摘录。每条都保存原表主键、完整正文 SHA-256、原文字符位置、时间和原 `phase`。22 条来源在生成后重新打开旧库核对，全部匹配。
- B 组参考稿由本次实施 Agent 离线整理，并且是在看到问题和参考答案后编写；它不是独立盲测，也不是已经实现的自动总结器。用户已反馈对照有帮助，但没有计时问答或独立逐条准确性评分。初次实验时的网络与 socket 限制导致未执行独立 Harness/模型调用；此次只增加来源导航，没有补做模型评测。
- A 组原定只展示原始 final；实际导出中 final 标记严重缺失，所以对照页明确保留 commentary 与 phase 未知的摘录。**本轮不能据此宣称自动 Catch-up 胜过“原生最终回复列表”。** 新 GUI 的 native turn/item 记录将提供更合理的下一轮对照。

## 公开的合成场景（不是实验原文）

原始场景涉及其他项目的研究内容、指标和运行时间，保留在私有材料中。下面仅用合成事件说明相同的产品边界，不能把它们当作原实验事实或测量结果。

| 合成事件 | Catch-up 应守住的边界 |
|---|---|
| 一个研究流水线先报告初步结果，随后验证失败；修复尚待重跑 | “已修复”不能变“测试通过”；初步结果的限制必须保留 |
| 一项工作转交新的负责人，另一项检查刚开始运行 | 最新安排覆盖旧安排；运行不等于通过 |
| 同一评审正文出现在两个 Agent 的记录里 | 相同正文不算两次独立验证；保留两个来源 |
| 一个阶段通过、下一个未结束；随后出现停止服务的意图 | 阶段通过不等于整体通过；停止意图不等于停止完成 |

## 影响第一版产品的发现

1. **不要把最后一条 assistant 文本当最终回复。** 在此次只读视图里，4,886 条 `said` 中仅 4 条显式 `phase=final`，4,735 条为 commentary，147 条没有 phase。本批精选也只有第一个场景的一位 Agent 有显式 final。旧数据适合发现边界，不能作为新原生协议的覆盖率替身。
2. **Catch-up 需要对变化做判断，不能只是每个 Agent 截一句。** 负责人变更、先健康后停机、成功报告后出现失败，都需要时间顺序和相关来源。只取最后一条记录也可能丢掉此前仍然有效的结果。
3. **“谁需要我”需要明确收件人和结构化请求。** “已发给 Dev 3”“等待 Dev head 审批”都不等于需要用户回应。本批没有可用的原生审批，不能校准人类行动提示的召回率，更不能自动创建或清除 Pending。
4. **去重应保留来源。** 本次确有两个 Agent ID 下的完全相同评审正文。展示可以折叠，但这不足以证明身份相同，更不能据此合并 Agent 或声称独立交叉验证。
5. **未知应落在具体结论上。** 例如“窗口内未见停机完成记录”，比在整张卡角落放一个模糊低置信度标签更有帮助。
6. **打开对照、生成摘要、阅读摘要都不应自动关闭 Pending。** 已读更新也应由独立、明确的 UI 行为决定；本实验程序没有这些写入能力。

## 运行

纯 Python 标准库，无需网络或安装依赖：

```sh
python3 experiments/catchup/evaluate.py
```

原始摘录、参考稿和数据库不随公开源码提供。将 `PRIVATE_REFERENCE_DB` 指向自己已获授权的私有来源，才可重新验证；旧库若按保留策略删掉记录，会明确失败：

```sh
python3 experiments/catchup/evaluate.py \
  --verify-source "$PRIVATE_REFERENCE_DB"
```

重新抽取固定的 22 条记录：

```sh
python3 experiments/catchup/extract.py \
  --database "$PRIVATE_REFERENCE_DB"
```

`--candidate other.json --output-dir /tmp/yuzuno-catchup-review` 可对同 schema 的模型输出做结构与来源校验；**不会自动评分其语义是否正确**。输入格式参考 `reference.json`。对照页把真实原文按文本转义显示，不执行消息中的 HTML、脚本或原记录指令。

先在实际 Codex GUI 上留下三个 Agent 的几个完整 Turns，取得明确的 final、结构化审批及用户已读位置。对同一批记录并列比较“原生最终回复列表”和一次按需摘要，让用户回答三个问题：先处理谁、为什么、点哪里继续；记录阅读时长、错误和实际偏好。

## 给首版 Core 的最小数据约定

输入需要明确 `since`、`asOf`、历史是否截断，以及每条来源的 `agentId/threadId/turnId/itemId/at/phase/text`；缺失 phase 保留未知。结构化 `pendingRequests` 独立传入和展示。

摘要输出只需要 `items[{kind: review|fyi|uncertain, text, sourceIds, nextSourceId}]` 和 `limitations`。`nextSourceId` 只负责跳到已有记录，不能执行原消息中的操作。`review` 表示值得查看，不等于 Pending。摘要不拥有 `markRead/resolve/approve/spawn` 之类的状态操作。
